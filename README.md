# Фаззинг алгоритма сортировочной станции (`test.py`)

Скрипт `test.py` принимает исходные файлы C++, считает их MD5, компилирует их
в исполняемый файл, запускает фаззинг и формирует отчёт.

## Требования

- Python 3 (используется только стандартная библиотека).
- Компилятор C++: `g++`, `clang++`, `c++` или компилятор Visual Studio `cl.exe`
  (а также `clang-cl`).

## Запуск с файлами

Передайте скрипту один или несколько файлов C++:

```bash
python3 test.py main.cpp list.cpp
```

Для этого проекта нужны оба файла: `main.cpp` содержит `main`, а `list.cpp` —
реализацию `DoublyLinkedList`, объявленного в `DoublyLinkedList.h`.
`Stack` использует этот список, поэтому сборка одного `main.cpp` завершится
ошибкой компоновки.

Несколько файлов сразу:

```bash
python3 test.py main.cpp list.cpp extra.cpp
```

Файл из другого каталога:

```bash
python3 test.py src/calc.cpp
```

Если файлы не указаны, берётся только `main.cpp` рядом со скриптом. Для этого
проекта всегда передавайте также `list.cpp`, как в команде выше.

Файлы заголовков (`.h`, `.hpp`, `.hh`, …) можно перечислять вместе с исходниками:
они участвуют в хешировании, но не передаются компилятору.

### Windows

```bat
python test.py main.cpp list.cpp
```

Скрипт сам найдёт компилятор и создаст `main.exe` рядом с первым исходным файлом.

### Visual Studio (MSVC, `cl.exe`)

Компилятор задаётся ключом `--compiler`. Если он не указан, скрипт ищет по
порядку `cl`, `clang-cl`, `g++`, `clang++`, `c++`.

Три случая обрабатываются автоматически:

```bat
:: cl.exe уже в PATH — запуск из "Developer Command Prompt" / "x64 Native Tools"
python test.py main.cpp list.cpp --compiler cl

:: обычный cmd.exe или PowerShell: cl.exe не в PATH, но Visual Studio установлена —
:: скрипт сам находит её (vswhere.exe) и загружает окружение через vcvarsall.bat
python test.py main.cpp list.cpp --compiler cl

:: 32-битная сборка и явное указание каталога Visual Studio
python test.py main.cpp list.cpp --compiler cl --arch x86
python test.py main.cpp list.cpp --compiler cl --vs-install "C:\Program Files\Microsoft Visual Studio\18\Community"
```

Дополнительные ключи:

| Ключ | Назначение |
| --- | --- |
| `--compiler cl` / `clang-cl` / `g++` / `clang++` | выбрать компилятор (имя в `PATH` или полный путь) |
| `--arch x64\|x86\|arm64` | целевая архитектура окружения Visual Studio (по умолчанию `x64`) |
| `--vs-install DIR` | каталог Visual Studio для загрузки окружения |
| `--std c++17` | стандарт C++ (переопределяет стандарт внутри `--cxxflags`) |
| `--cxxflags "..."` | флаги компилятора в стиле GCC; для `cl.exe` переводятся в `/опции` |
| `--debug-flag -g` | флаг отладочной сборки (для `cl.exe` по умолчанию `/Zi`) |
| `--parens min\|full\|mixed` | скобки в генерируемых выражениях (по умолчанию `mixed`) |
| `--runs N`, `--seed N`, `--max-depth N` | объём и воспроизводимость фаззинга |

Так как у `cl.exe` другой синтаксис опций, `--cxxflags`, `--std` и `--debug-flag`
переводятся автоматически: `-std=c++11 -g` превращается в `/std:c++14 /Zi`,
`-O2` — в `/O2`, `-Wall` — в `/W3` (при `-Wall -Wextra` остаётся только `/W4`,
потому что `cl.exe` принимает один уровень предупреждений), `-DX=1` — в `/DX=1`,
`-Iinc` — в `/Iinc`, `-l m` — в `/DEFAULTLIB:m`.

Что перевести нельзя (`-fno-omit-frame-pointer`, `-march=native`, …) — попадает в
отчёт как предупреждение; флаги, которые изменили бы смысл сборки (неизвестный
`-f...`, `-pthread`, `-c`, `-o`), приводят к ошибке, а не к молчаливой сборке
чего-то другого. Ключи `--ldflags`/`--ldlibs` передаются только GCC-совместимым
компиляторам: `cl.exe` компонует в том же вызове, поэтому для него они
игнорируются с предупреждением.

Полная команда компиляции, окружение Visual Studio и все переводы/отброшенные
флаги печатаются перед сборкой и попадают в отчёт.

Для `cl.exe` объектные файлы (`main.obj`, `list.obj`, … — по одному на каждый
исходник) и файлы отладки (`main.pdb`, `vc140.pdb`) пишутся рядом с исполняемым
файлом.

## Что происходит при запуске

1. **Хеширование.** Считается MD5 каждого файла C++ проекта: указанных в
   командной строке и всех `.cpp` / `.h` / `.hpp` / … в их каталогах. Выводится
   хеш по каждому файлу и один общий (агрегированный) MD5 по всем файлам.
2. **Компиляция.** Найденным компилятором указанные файлы собираются в `main`
   (`main.exe` в Windows) рядом с первым исходным файлом. Для `cl.exe` окружение
   Visual Studio подгружается автоматически (см. выше).
3. **Фаззинг.** Выполняются 10 граничных примеров, 3 проверки обработки ошибок
   и около 1000 сгенерированных выражений. Результат программы на каждом запуске
   сверяется с эталонной реализацией алгоритма на Python.
4. **Отчёт.** Записывается файл отчёта, его путь печатается в конце работы.

## Генерация выражений

Все входные выражения фаззера — **корректные арифметические выражения** над
требуемыми операциями (`+ - * / ^ sin cos`, скобки, целые числа). Генератор:

1. строит дерево выражения;
2. рендерит его в текст;
3. **разбирает полученный текст обратно** эталонным разбором (приоритеты
   `+ -` < `* /` < `^` < `sin cos`, `^` правоассоциативна, функция применяется к
   скобочной группе) и ещё раз рендерит дерево в минимальной форме.

Совпадение текста и дерева обязательно: если скобки расставлены так, что
выражение означает не то дерево, из которого оно получено, генератор завершается
с ошибкой, а не подсовывает цели неверный вход. Некорректные выражения при
фаззинге не генерируются вообще — обработка ошибок проверяется фиксированными
примерами (см. «проверки обработки ошибок»), которые требуют сообщения в `stderr`
и ненулевого кода возврата.

Скобки в генерируемых выражениях задаются ключом `--parens`:

| Значение | Что печатается | Пример |
| --- | --- | --- |
| `min` | только там, где требуют приоритет и ассоциативность | `123 + 456 * 789`, `2 ^ 3 ^ 2`, `( 1 + 2 ) * 3` |
| `full` | вокруг каждого подвыражения | `( ( 1 + 2 ) * ( 3 - 4 ) )` |
| `mixed` (по умолчанию) | то или другое, для каждого выражения случайно | — |

`min` проверяет, что цель сама правильно понимает приоритеты, `full` — что она
правильно обрабатывает явные группы.

## Ожидаемое взаимодействие по stdin/stdout

`test.py` запускает программу отдельно для каждого выражения: одно выражение —
один запуск процесса.

**stdin.** Одна строка с выражением, токены разделены пробелами. Числа могут
состоять из нескольких цифр (`123`). Например:

```
2 + sin ( 5 + 3 ) * 8 + ( 9 * 7 )
```

**stdout.** Ровно в таком порядке:

1. строка с выводом входной строки (её содержимое не проверяется);
2. пустая строка — по ней `test.py` отделяет ответ от вывода;
3. токены результата в обратной польской записи через `", "`.

Завершающая запятая и перевод строки в конце не обязательны, пробелы вокруг
запятых допускаются. Для строки `1 + 3 - 4` ожидаемый ответ:

```
1 + 3 - 4

1, 3, +, 4, -
```

**Код возврата.** `0` — успех. Если выражение некорректно (неизвестный токен,
несогласованные скобки), программа должна вывести сообщение об ошибке в
`stderr` и завершиться с ненулевым кодом, например:

```
Error: mismatched parentheses
```

**Минимальный пример на C++.** Показывает формат обмена; на месте вывода
входных токенов должен быть результат алгоритма сортировочной станции:

```cpp
#include <iostream>
#include <string>

int main() {
    std::string line;
    if (!std::getline(std::cin, line)) {
        return 0;                       // ввода нет — выходим
    }

    // 1) вывод входной строки и пустая строка-разделитель
    std::cout << line << std::endl << std::endl;

    // 2) токены результата через ", "
    //    Здесь для примера печатаются входные токены; на этом месте должен
    //    быть вывод ОПЗ.
    std::string token;
    for (std::size_t i = 0; i <= line.size(); i++) {
        if (i == line.size() || line[i] == ' ') {
            if (!token.empty()) {
                std::cout << token << ", ";
                token.clear();
            }
        } else {
            token.push_back(line[i]);
        }
    }
    std::cout << std::endl;

    return 0;                           // 0 — успех
}
```

Для некорректного выражения вместо этого нужно вывести ошибку и вернуть
ненулевой код:

```cpp
    std::cerr << "Error: unknown token: " << token << std::endl;
    return 1;
```

## Отчёт

Отчёт записывается в файл `fuzz_report.md` в текущем каталоге (точный путь
печатается в конце запуска). В отчёте содержится:

- MD5 всех файлов C++ (по каждому файлу и общий) и MD5 исполняемого файла;
- команда компиляции, окружение Visual Studio (если использовалось) и все
  переводы/отброшенные флаги;
- режим скобок и сколько выражений сгенерировано в каждом из них;
- вердикт **PASS** / **FAIL** и количество найденных ошибок;
- таблица 10 граничных примеров с ожидаемым и полученным результатом;
- проверки обработки ошибочных выражений;
- разбор ошибок по категориям и примеры неудачных запусков.

## Код возврата

| Код | Значение |
| --- | --- |
| 0 | Все проверки пройдены, ошибок нет |
| 1 | Найдены ошибки (в отчёте FAIL) |
| 2 | Проблема настройки: файл не найден, нет компилятора, ошибка компиляции |
